## 一、两张照片：菜单是中文，值是黑块

2026-11-26 早上 07:47，guo 发来两张照片：SETUP MENU > DISPLAY 的列表。菜单项名——目标位置、罗盘——都是中文，显示正常；但每一项下面的当前值，是一整块深色空白矩形。点进选值屏也一样，两个选项的位置同样是黑块，字出不来。

我起初把照片认成了 5DR。guo 09:33 亲口纠正：照片是 2DR，他刷的是县级版前一版（2DR 即 SUB v8 + MAIN v9）。这个纠正很重要，后面会再提到——三台的黑块来源并不相同，认错机器就修错地方。

照片里那两项值，本来应该是：

| 菜单项 | 应有的值 | 英文原值 | mask |
|---|---|---|---|
| 目标位置（TARGET LOCATION） | 罗盘 / 数字 | COMPASS / NUMERIC | A000 |
| 罗盘（COMPASS bearing） | 航向向上 / 北向上 | HEADING UP / NORTH UP | NORTH UP A800、HEADING UP AA00 |

这四个值在 DISPLAY 里是最显眼的——开机进菜单第一眼就是它们。值翻译本身没问题：串、mask、字形，逐项核对都对。问题不在值本身，在值是怎么被画出来的。

## 二、三级值是什么，v7 做了什么

三级值是 SETUP MENU 里每个设置项下面那行小字：当前取什么值。菜单分三级——一级是 12 宫格分类，二级是菜单项名，三级是项下的当前值。显示汉化（第 23 篇）做的是二级菜单名；输入（第 25 篇）做的是选字字典；三级值是最后补上的一块：把英文值翻译成中文，显示在项名下方和点进去的选值屏里。

三级值翻译版是 3DR SUB v10、2DR SUB v7、5DR SUB v7，只加值翻译、MAIN 不动。3DR 与 2DR 各译 64 个值，每台仍有约 83 个值未译，不在本次修复范围。

v7 的做法很轻：对全部值绘制点，只改最后 4 个字节的 BSR（分支到子程序），让它改指一段 16 字节的 stub：

```
fb 42 新串 / fb 3e mask / BSR JIS_R / RTS
```

stub 加载新中文串、装 mask，然后跳去固件自带的 JIS 渲染器（JIS_R）画出来。改动小、风险看起来低——这正是它出问题的原因。

---

## 三、根因：JIS_R 带着旧状态跑

一个值是怎么画到屏幕上的：固件里每个值都有一段叫 thunk 的小代码，负责把串指针、mask、坐标这些画图要用的状态装好，再 BSR 跳去渲染器。v7 只改了 thunk 末尾的 BSR，thunk 前面的部分原样不动。这对 JIS 起源的绘制点没问题——它的 thunk 本来就是 JIS 形态，前置那几条指令与 JIS_R 是一套的。

但对另外两类起源的绘制点，thunk 在 BSR 之前仍会执行渲染器专用的前置指令，JIS_R 带着那套旧状态跑，字形画出来就是实心黑块：

- **SB 起源**（单字节渲染器）：thunk 前置是 `fb 22` / `fb 32` 装串指针、`a0 0a` / `a0 0b`、`5f 11`、`62 22 5f 22` 等，这些是为 SB_R 配的状态。
- **D5D8 起源**（单字节值渲染器，2DR）：thunk 的 setup 长 14–24 字节，以 `7e a4` / `7e a5` / `7e a2` 开头，这些是为 D5D8 配的状态。

为什么菜单名没事？菜单层早就知道这一点：SB 主段的菜单项用的是 `convert`——**整个 thunk 跨度重写**为 `fb 42 新串 / fb 32 mask / BSR JIS_R`，前置指令清得干干净净，菜单名显示正常。值构建对这些点只改 BSR，是整个系列里唯一用错机制的地方。

值串、mask、字形格、stub 本体、BSR 目标，此前已逐项核对无误，全部排除在外。渲染器地址如下（VA 基址 file + 0xFFC00000）：

| 机型 | SB_R | JIS_R | D5D8 |
|---|---|---|---|
| FT-5DR | 0xFFF46FF1 | 0xFFF5142C | — |
| FT-3DR | 0xFFEF1B23 | 0xFFEFA7E7 | — |
| FT-2DR | 0xFFF6D6A1 | 0xFFF76175 | 0xFFF6D5D8 |

5DR 的 JIS_R 与 3DR 的逐字节同构（仅一处地址常量不同），差异在调用点的前置状态，不在渲染器本身。

## 四、三台来源不同

三台的已译值绘制点，按起源分是三张不同的表：

| 机型 | 已译值 | 绘制点 | SB 起源 | JIS 起源 | D5D8 起源 | DISPLAY 四值 |
|---|---|---|---|---|---|---|
| FT-5DR | 23（SB 点覆盖） | 44 + 109 | 44 处 | 109 处 | 0 处 | 全 SB 起源 |
| FT-3DR | 64 个 | 155 处 | 45 处 | 110 处 | 0 处 | 全 SB 起源 |
| FT-2DR | 64 个 | 162 处 | 0 处 | 95 处 | 67 处 | 全 D5D8 起源 |

DISPLAY 四值的绘制点地址（文件偏移）：3DR 是 COMPASS @0x3006E1、NUMERIC @0x300702、NORTH UP @0x300743、HEADING UP @0x300764；2DR 是 COMPASS @0x8D9C9、NUMERIC @0x8DA05、NORTH UP @0x8DA5D、HEADING UP @0x8DA99。两台的 DISPLAY 四值全是“坏起源”，所以照片里 DISPLAY 这一屏全黑得最彻底。

证据状态要分开说，**三台不一样**：

- **2DR 是照片实证**：guo 手里那台，照片就是它的问题。67 处 D5D8 点的 setup 经扫描复现，162/162 界限分明——D5D8 点全以 `7e a4` / `7e a5` / `7e a2` 开头，JIS 点全以 `5f XX` 开头。
- **5DR、3DR 是二进制实证**：45 / 44 处 SB 点的 thunk 跨度内全部含有 `a0 0a` / `a0 0b`，逐项核对过。**但黑块未在 guo 的 5DR / 3DR 真机上被照片证实**，验收时要留意。

这里还有个插曲：3DR 的修复报告里一度写着“2DR 不用修”——因为 2DR 的已译值里 SB 起源是 0 处，不含 SB 缺陷。这个结论是错的：2DR 的缺陷是 D5D8 起源，不是 SB 起源。是 guo 那句“照片是 2DR”把这条线纠了回来。按起源分类之前，先确认缺陷到底有几种来源。

## 五、修复：整个 thunk 重写

修复就是把值绘制点也改成菜单的做法：**按 `convert` 重写整个 thunk 跨度**，不再只改 BSR。重写后的形态：

```
fb 42 新串VA / fb 32 mask（32 位）/ [75 42 <x>] / BSR JIS_R / 填充
```

几个细节：

- `75 42 <x>` 是 thunk 里原有的 X 坐标设置，DISPLAY 四处是 `75 42 41`（X=65），原样保留；没有坐标设置的点不补坐标，坐标由调用方提供。2DR 的 67 处跨度内本来就没有 `75 42`，坐标全由调用方提供。
- 填充用 `66 04`（mov #0, r4）与 `75 43 00`（mov #0, r3），画完即死，无害。
- JIS 起源的绘制点本来就是对的，保持 stub 不动。旧 stub 留在表里，不再被调用。
- 改动只限值绘制的代码段，其余全部不动：值表、字形、县级字典（1,614 字）、输入记录码、菜单翻译、MAIN。

影响范围要说清：受影响的是三级值翻译版（v7 / v10）及之后的所有版本，**包括县级版**——县级版继承了这个问题，不是县级扩充带出来的。县级版与三级值版的值代码区逐字节一致（3DR 是 0x2E0000–0x310000 与值表 0x352600–0x352BE8），县级扩充没动值绘制。这是三级值翻译版构建引入的问题，不是原厂 bug。

## 七、刷机与验收

1. SETUP MENU > DISPLAY 列表：目标位置、罗盘、背光、对比度、开机信息五项都能点进，值显示英文是正常的；

## 八、更正

此前“三级值照片三处全覆盖”的说法，**未在任何一台真机上证实过**，不要再引用。v7 / v10 构建报告里所谓“照片验证”，一律视为未证实，以本次修复版的真机验收为准。

照片覆盖不等于真机验证。显示类问题只认真机——这句话这个系列已经是第三次学到：第一次是显示 v1 的菜单通道（英文表不是日文通道），第二次是末位表（文件级 diff 查不出“机器读的是哪份数据”），这次是值绘制（stub 法在纸面上自洽，真机上黑块）。文件级验证能保证“补丁落在预定区域、逐字节无误”，保证不了“机器运行时读的正是这份数据”。后者只能靠把每条通道追到源头，再用真机把每个观测量对上。

## 结尾

回头看，这次的 bug 形态和之前两次一模一样：**改对其中一条，不等于改对全部**。值绘制有三类起源的 thunk，v7 只按其中一类（JIS）写了补丁，另外两类（SB、D5D8）的前置指令原样留在原地，JIS_R 带着它们跑就画成黑块。菜单层当初用整段重写，就是因为它知道前置指令不能留；值构建图省事只改了跳转，省掉的 4 个字节，最后要 891 / 954 / 1,711 个字节还回来。

好消息是修法本身不冒险：整个 thunk 重写是菜单已经真机验证过的路，JIS 点不动，值表、字形、字典、MAIN 全不动，县级地名一个字不少。等 guo 把三件修复版刷上真机，DISPLAY 那一屏的罗盘、数字、航向向上、北向上，应该就能正常显示了。
