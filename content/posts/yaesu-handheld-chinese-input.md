# 给八重洲手台做中文输入：从 706 字到地名全覆盖

> 菜单是中文了，可信道名还是打不出一个汉字。
>
> 这篇记录的是给 FT-3DR、FT-2DR、FT-5DR 三台手台补上中文输入的全部过程：一张借来的日文字典、731 个地名的大考、三条互不相认的数据通道、一张按原厂字数算死的「末位表」，最后是严格拼音重排和入口搬迁。解密与显示汉化的过程在[第 23 篇](/posts/yaesu-handheld-chinese-firmware/)，这篇是它的续集。

## 一、显示汉化简史（一笔带过）

显示部分是第 23 篇的主体，这里只留一条主线，因为输入这条线完全站在它上面：

- **v1 通道搞错**：把中文写进了固定菜单名表（文件 0x3DF4D，119 条 × 20 字节）。那张表是**英文通道**——英文模式逐字节按单字节 ASCII 渲染，中文写进去变成乱码（真机照片里 DISPLAY 项显示成 `L\I80LCV / MeHW / IQCJA]IA…`，与 v1 中文表逐字节按 ASCII 读出来完全一致）；日文模式根本不读这张表，菜单还是原厂日文。
- **真相**：日文菜单名**没有表**。绘制时由分发代码逐项拼装，每项最多三段：单字节段（SB，画 ASCII 和半角片假名，承载不了汉字）、双字节段（JIS，按原始 JIS X 0208 码对绘制）、硬编码单字段（CHAR，多半是「設」「定」这类后缀）。
- **v2 修法**：段字符串一个不动，只改**绘制点**——把每项的主段改接固件自带的 JIS 渲染器，去画一条新中文串，新串放在擦除区的新表里，其余段绘制中和掉。3DR 共 117 个拼装全部有中文名（绘制点转换 45、指针重定位 5、跳板 50、池翻译 14、标识符保留 3）。
- **字形四轮**：最初用 Fusion Pixel 字体缩放进 14×14 字格，真机评价是笔画粗细不匀、不如原厂原生字体。最后换**文泉驿点阵宋体** `wenquanyi_13px.pcf`（PIXEL_SIZE 14 的原生 strike，墨迹恰好 13×13）的原生位图，零缩放、零削字，83 个替换字形。2026-11-21，我在 3DR 真机上确认「完美中文显示」，显示版定案。
- 2DR、5DR 跟进同一打法，各自在本机镜像上重新坐实偏移：2DR 显示 v2 转换 97/112 项，5DR 显示 v2 处理 121 个拼装（绘制点转换 104 项）。两台的 v1 都犯了同一个通道错误，一并作废。

显示定案之后，剩下的短板很具体：菜单、设置、值标签都是中文了，但**给信道起名、写呼号备注时，一个汉字都输不进去**。原厂的文本输入只有英数、片假名和符号。

## 二、发现：原厂自带一套汉字选字输入

拆 3DR 的 SUB 明文找输入子系统，先纠正了自己的一个前提：原厂输入并不是「只支持英数、片假名、符号」——SUB 里躺着一整套**汉字选字输入**，日本用户录汉字走的就是它：

- **类别索引**：文件 0x2D49E0 起 45 条 × 8 字节，`{key 码, 记录指针}`。44 条 key 是平假名（あ…わ，只取清音），第 45 条 key 是「記」，指向符号表——key 里混着一个不可能是读音首假名的「記」，说明 key 是给用户点的**类别页签**，不是匹配键。
- **候选字典**：文件 0x3A716–0x3D236，44 条记录与索引一一对应，格式是 u16 大端的原始 JIS X 0208 码内联数组，无表头、无长度字段，尾部以 0x0000 填充。总容量 **5,520 码**，实际使用 **4,605 码**，去重后 3,200 个不同的码（同一汉字在多个读音组重复出现，是转换字典的典型形态）。单条最大的是「し」组：容量 480、用 447；「か」组容量 360、用 337。这两个数字记住，后面要出大事。
- **符号表**：158 条，与字典共用同一索引、同一消费代码。
- **网格几何**：消费代码纯算术寻址，`记录基址 + 页×0x50 + 行×0x10 + 列×2`——**8 列 × 5 行、每页 40 字**（2DR 是 8×7、每页 56 字）。
- **英数和片假名没有表**：全镜像扫描无命中，它们是编辑器在连续码段内的算术循环，不查表。

机制一句话：**选读音首假名 → 该组全部候选以网格分页呈现 → 点选**。字典里不存读音字符串，固件没法按完整读音过滤候选，呈现单位是整组（「し」组 447 字 = 12 页，靠翻页肉眼找）。

### 拼音输入为什么做不了

顺手把拼音输入判了死刑：固件里**没有任何拼音基础设施**——没有拼音音节表、没有拼音→汉字词库、没有组词和候选窗的状态机。连原厂的「変換」都只是首假名分组加整组网格点选，按完整读音过滤都做不到。拼音输入等于从零写一个输入法子系统再以机器码补丁注入编辑器事件循环，与改表、改绘制点完全不在一个量级。**不做。**

### 借壳的账

选字表这条路则每一环都有现成证据：索引改写一条 → 记录写空闲区 → 网格渲染固件自带（画任何 JIS 码）→ 字形与显示版同一套码空间（选出的码经同一个单字 worker、同批 14×14 字格显示）→ 存储回显与原厂汉字录入同一路径。字形侧也不缺货：字库 7,434 个有字形的码里汉字占 6,485/6,486，冷僻二级字可捐赠的格子保守估计 2,000 个以上，需求只有几百。

代价先说清，是所有借码方案的固有属性：**名称字段里存的始终是载体 JIS 码**。用电脑端 CPS 读出来、或克隆到一台没改过的机器上，显示的是载体码对应的原日汉字，不是简体字。APRS 报文这类按 ASCII 走的字段同理，中文只适合本地信道名这种场景。

## 三、706 字精选集，与地名覆盖审计的打击

第一版字集 706 字：以 GB2312 一级字高频段为骨架，叠加电台术语构词用字（电台、信道、哑音、中继、差频、驻波……）、省市地名常用字、方位、数字汉字与单位。排序沿 GB2312 一级码序——它本身就是拼音序骨架（同音按笔画）。这里有个小坑：拼音首字母的页码边界，我逐个按 GB2312 标准锚点字核实过（啊 B0A1、芭 B0C5、擦 B2C1……），网上流传的边界表有几处是错的（会把「双水谁顺说思四松苏」一段误标成 t 段），没采用。

落字分三种：

| 模式 | 字数 | 说明 |
|---|---|---|
| 直用 | 485 | JIS 内且同形，原码原形 |
| 对应字换形 | 194 | 码位是繁体/日式形（如 爱→愛 0x3026），码位不变、字形格换文泉驿简体位图 |
| 捐赠码 | 27 | JIS 内根本没有此字，借冷僻二级码（如「卡」借 0x505E） |

挂载方式（3DR SUB v6）：改写索引第 43 条——原「わ」组牺牲掉，key 改「中」（JIS 0x4366，页签直接显示「中」），指针改指空闲区 0x351210 的新表，706 码加 14 个空槽凑满 720 槽 = 18 页。字形替换 175 格。2DR、5DR 同构跟进（SUB v3）。

然后我拿全国地名给这张表做了一次审计，结果不好看：

- 口径：地级行政区 333 个 + 县级市 398 个，合计 **731 个**名字（据维基百科名单整理，数量与民政部公布口径一致），只查专名本身。
- **能完整打出的只有 214 个（29.3%）**：地级 103/333（30.9%），县级市 111/398（27.9%）。
- 共缺 **366 个不同的字**。缺字影响最大的：兴（15 个地名）、尔（14）、德（13）、昌（13）、阿（11）、石（9）、临（9）。
- 最扎眼的是「石」不在表里——**石家庄打不出来**。唐、沈也不在：唐山、沈阳都打不出来。

706 字集是按「电台常用字」筛的，从没按地名过一遍，地名用字又偏生僻，三成覆盖就是这么来的。审计附带产出了一张贪心补字表（补哪个字能解锁几个地名），但真正的解法不是补几十个字——是把 366 个缺字全量装下。

## 四、三条通道连环坑

706 字版刷上真机，三个症状一起出现：

1. **翻页封顶**：明明装了 18 页，翻到第 2 页就翻不动了；
2. **选入错位**：网格里点第 2 页的「産」，存进信道名的却是「腕」——有照片实证；
3. **光标只能在第一行左右移动**。

根子是一个我事先没意识到的架构事实：**这本字典在 SUB 和 MAIN 两颗 CPU 里各存一份物理副本，三条路径各读各的**：

| 路径 | 读哪份 | 作用 |
|---|---|---|
| 显示（页签标签 + 网格） | SUB 索引 → SUB 记录 | 屏幕上看到什么 |
| ENT 选入 | MAIN 记录（经描述符地址） | 按下确认存进哪个码 |
| 翻页计数 | MAIN 运行时扫描**物理原址记录** | 能翻几页 |

### 第一坑：只改 SUB（单表版）

v6 只改了 SUB：显示全对，但 MAIN 里还是原厂字典。MAIN 的「わ」记录只有 48 个码，所以计数封顶 48 → 只能翻 2 页；ENT 按 MAIN 的表读码，「わ」记录第 47 槽（0 起）正是 0x4F53「腕」——屏幕上那个位置显示的是新表的「産」，存进去的却是「腕」。显示槽位和存入码位逐字对上，通道模型就此坐实。

### 第二坑：MAIN 描述符重定向（选入修好，计数仍封顶）

修法看起来顺理成章（3DR MAIN v7，2DR、5DR 的 MAIN v4 同）：在 MAIN 的空闲区（3DR 是 0x7C000）写一份同样的 706 码新表，再把「わ」的描述符地址字段改指新表（3DR 在文件 0x7679A：`00 07 B0 80` → `00 07 C0 00`）。只动 1,416 字节。

真机结果：**ENT 选入修好了**（点「産」存「産」），**翻页还是封顶 2 页**。

这一刀把计数通道的性质切了出来：计数不经描述符。后续追查把其余可能性逐个排掉——SUB 侧证明页号是外部「给定」的（候选控件的 model 结构里页号字段由画面之外的层写入，SUB 只负责按给定页号绘制，绘制代码对页号无钳制）；MAIN 的 45 条描述符逐字节全解，除记录地址外只有模板变体位，**没有任何计数字段**；used 列、容量列、页数列在两颗 CPU 的镜像里按 u8/u16/u32、大小端全编码搜索，**零命中**。排除法剩下的唯一解释：MAIN 的変換引擎在运行时**扫描物理原址那条记录**得到计数，扫描起点不经描述符字段。

还有个原理性的麻烦：原厂 45 组的 used 都恰好落在各自容量的最后一页内，所以「扫终止符数 used」和「按容量算页数」在原厂数据上给出的页数逐组相同、不可区分。修复方案必须在两种机制下都成立。

### 插曲：5DR 的 MAIN 刷错包

同一时期 5DR 还出了个岔子：用 EXP 包做底的 MAIN 刷进国行机，机器报「固件错误」不能正常启动，换八重洲中国官网的 CHN 包重刷才恢复。事后逐字节比对两个官方包：

- **SUB 是同一个文件**：两包的 SUB exe 同名、同尺寸、SHA256 完全一致（`436284d2…`），连区域后缀都同为 (ENG)。所以所有 SUB 构建的底子没错，不用重做。
- **MAIN 是同版本、不同构建**：都标 Ver.1.21、同尺寸，但明文 diff 达 446,602 字节（42.6%）。更新包尾部的区域串是 `CHN` 对 `EXP`、机型串是 `FT5DR(MAIN)` 对 `FT5DR/E(MAIN)`；CHN 构建的区域名表里有 CHN 条目，EXP 构建里连 "CHN" 这个字符串都不存在。两个包的加密种子时间戳只差 12 分钟，是同日双区域构建。

结论：5DR 的 MAIN 自此一律以 CHN 包为底；3DR 的 EXP 包 MAIN 写链则由 v7 真机刷写单独证明可用，两台分开看待。

### 方案 A：物理分片写

计数既然认物理原址，就把码写回物理原址：706 字拆两片（479 + 227）写进组 11「し」（容量 480）和组 5「か」（容量 360）在 MAIN、SUB 两侧的物理记录，描述符与索引指针**全部保持原厂**，v7 的重定向补丁回退，「わ」组恢复原厂。两种计数机制下页数都成立（扫描数得出 479/227，按容量算是 480/360 的整页数，只多不少）。产物：3DR SUB v7 + MAIN v8、5DR SUB v4 + MAIN v5（CHN 底）、2DR SUB v4 + MAIN v5。

## 五、方案 3：全地名覆盖，三片 1,075 字

分片路线通了，字集扩容就是算术题：706 + 369 个地名缺字 = **1,075 字**（睢、王、岚三个审计点名外另行核查的字也并入）。369 个新字的落字：直用 233、对应字换形 13、捐赠码 123，「无法落字」清单为空。

容量账：两片实装 479 + 359 = 838，装不下。按全 45 组实测容量选第三大组 25「は」（容量 240）作第三片：

| 片 | 宿主组 | 容量 | 实装 | 页数 | 页签标签 |
|---|---|---|---|---|---|
| 1 | 组 11「し」 | 480 | 479 | 12 | 中 |
| 2 | 组 5「か」 | 360 | 359 | 9 | 漢 |
| 3 | 组 25「は」 | 240 | 237 | 6 | 地 |

每片留 1 槽放终止符，所以三片的扫描页数与容量页数恰好相等（12/9/6），末页分别是 39/39/37 字，**没有空白页**。物理记录整段重写，两侧同码序；指针仍全原厂。

2DR 被容量逼出一个偏差：它三片可用码位只有 447 + 391 + 223 = 1,061，比 1,075 差 14 码，只能加第四片——借组 15「た」装最后 14 个字，标签「名」。2DR 的页宽也不同（56 字/页），四片是 8/7/4/1 页。

构建脚本内断言地名复验：**731/731**。原先打不出的 517 个名字逐字可打，366 个缺字全在集内。版本：3DR SUB v8（`908c184c…`）+ MAIN v9（`9e339633…`）；5DR SUB v5（`592b19e7…`）+ MAIN v6（`3198a711…`，CHN 底）；2DR SUB v5（`30bfa574…`）+ MAIN v6（`f9edfa19…`）。

刷上真机：三片翻满、选入对位、石家庄和淄博都能输了。但验收时又摸到一个新问题——每张表的最后一页，选字选不到底。

## 六、最后一页选不到字：末位表

症状报回来很具体，我拿教程附表逐个对位置：

| 机型 | 表 | 表现 | 停住的字 | 在该片的位置 |
|---|---|---|---|---|
| 3DR | し（中片） | 只能选到「厘」 | 厘 | 第 447 个 |
| 3DR | か（漢片） | 只能选到「温」 | 温 | 第 337 个 |
| 3DR | は（地片） | 末页光标钉在「洲」，不能左右 | 洲 | 第 201 个（末页首格） |
| 2DR | か | 末页钉在「铜」 | 铜 | 第 337 个（末页首格） |
| 2DR | し | **能选到最后一个字** | 厘 | 第 447 个（恰为片尾） |
| 2DR | は | 只能选到「洲」 | 洲 | 第 201 个 |

447 和 337 正是第二节里让记住的两个数字——组 11、组 5 的**原厂 used**（字典分析时实测：し 容量 480/用 447、か 360/337）；201 是组 25 的原厂 used，本次实扫确认。点屏点选同样选不到，说明不是旋钮事件的问题，是候选控件拿到的「可选总数」本身被钉死。

追查结论：**MAIN 里有一张 44 组的「末位表」**。3DR 在文件 0x1BDDA 起，44 组 × 2 字节（前置结构是组数 `00 2C` 和 44 个假名码块）；2DR 同构，表在 0x1A26C。每组存一对：

```
(末页号, 末页内末格号) = ((used − 1) ÷ 页宽, (used − 1) mod 页宽)
```

可选下标上限 = 末页号 × 页宽 + 末格号 = **原厂 used − 1**，与记录内容毫无关系——所以物理记录全换成 479/359/237 之后，上限还停在 447/337/201。对全部 44 组逐组验算 `P×W + C + 1` 与原厂 used 对照：3DR 44/44、2DR 44/44 全对。六个真机实测点也逐个吻合，连「2DR 的し片为什么不咬」都有解释：它的片大小 447 恰好等于原厂 used 447，钳制值正好落在片尾。

还有个细节值得记：翻页页数此前一直正常，是因为页数对总数口径不敏感（⌈479/40⌉ = ⌈447/40⌉ = 12），末位钳制是第一个把「两套总数口径不一致」暴露出来的观测量。文件级 diff 审计查不出这种问题——它只能证明「我改的地方都对」，证明不了「屏幕真正读的是我以为的那份数据」。这已经是这个系列第二次学到同一课（第一次是显示 v1 的菜单通道）。

修复就是按新片大小重算三个条目。3DR（页宽 40）：组 5 `08 10` → `08 26`（上限 336 → 358）、组 11 `0B 06` → `0B 26`（446 → 478）、组 25 `05 00` → `05 24`（200 → 236）。只动 MAIN，SUB 无副本。

## 七、严格拼音重排

三片版的字序是 GB2312 骨架序：同音节内按笔画/部首排，二级字插在同音锚点附近。能用，但有十几个「错位字」不在自己的拼音首字母段里（葛、嘉、佳、慈、滁、楚、徐、鸭、崖、雅），翻表找字时很别扭，尤其地片（从 X 段中间切进来）看起来最乱。趁着末位表要重出 MAIN，把字序一并换成严格拼音序——排序细节我全权定了：

- **排序键**：完整拼音音节字典序（a、ai、an、ang、ao、ba……；ü 按 v 排在 u 之后）→ 声调 1→2→3→4→轻声 → 笔画升序 → GB2312 原序兜底。
- **数据来源**：拼音用 pypinyin 0.55.0 默认读音，与 Unihan kMandarin 全表交叉核对，仅 4 处分歧；笔画用 Unihan kTotalStrokes，1,075 字 100% 覆盖。
- **结果**：993 个字位置变化；错位字全部自然归位——滁 886 → 102、楚 887 → 104、慈 735 → 111、佳 616 → 342、嘉 615 → 344、葛 402 → 231、徐 959 → 886、鸭 994 → 895、崖 995 → 897、雅 996 → 899。
- **多音字归位**：跨音节多音字 120 个按最常用读音归位，另有 108 个仅声调异读（只影响段内声调位）。7 个字经人工改读：佛 fó、甸 diàn、厦 xià（取厦门，不取大厦的 shà）、长 cháng、泊 bó（取停泊）、匙 chí、薄 bó。济按 jì 归位（经济/救济），济南的 jǐ 是异读，没取。
- 一个任意性注明：「嗯」是唯一的语气词，读音作 ń（音节 n），落在 n 段之首（第 558 位），这个位置怎么放都有点任意。

码位、字形、分片大小全不动，只换顺序。

## 八、入口搬迁：あ / か / さ 一下直达

还剩最后一个逻辑问题：入口。三片的宿主组是按容量选的，入口键位毫无逻辑——中片挂在「し」上，し 不是行首字，要在假名键盘上连点「さ」两下才出；漢片的「か」、地片的「は」都是行首字、按一下就行。第一张、也是最大的表，偏偏要多按一下。

改法：三张表改挂到**最前面三个行首字**——あ → 中、か → 漢、さ → 地，全是一下直达、顺序连排。か 的宿主组 5 本来就在位（359 ≤ 360 原位装下）；组 0「あ」和组 10「さ」的原记录跨距只有 160/200 码，装不下 479/237，**记录整体搬迁到镜像空闲区**：MAIN 改描述符[0]/[10] 的地址字段、SUB 改索引[0]/[10] 的指针，末位表改新宿主的条目（组 0 = `0B 26` 对应 479、组 10 = `05 24` 对应 237，页宽 40）。腾空的「し」「は」两组完整恢复原厂——记录、索引 key、末位表条目全部回 stock，刷完打し/は 回到原厂日文候选；组 0/10 的原日文字随之让位（与此前各组让位同性质）。2DR 同理（它的 SUB 空闲区原选地址被旧数据占着，构建时改用了另一段经双边验空的区域），14 字的「名」片仍挂「た」不动。

一个机型差异：排序表的码位是 3DR 口径，2DR 有 25 个字、5DR 有 22 个字用的是本机自己的捐赠码，构建时按字映射各机基线的码位，字序不变。

SUB 侧的记录搬迁加索引改指，是这个系列第一次做（MAIN 侧有 v7 的先例且真机已证）。静态验证只能查字节，这一步的风险只能靠真机验——结果见下一节。

## 结尾

回头看这条线，每一步的坑都是同一类：**固件里同一份数据有好几个副本、好几条读取路径，改对其中一条不等于改对全部**。显示那次是「英文表不是日文通道」，输入这次是字典双份存、三路各读各的，最后还藏着一张谁都没改过的末位表。文件级验证能保证「补丁落在预定区域、逐字节无误」，保证不了「机器运行时读的正是这份数据」——后者只能靠把通道逐条追到源头，再用真机把每个观测量对上。

至于成果本身：三台手台现在菜单是中文、信道名能输中文，731 个地名全覆盖，入口是假名键盘上最顺手的三个键。代价也还是那些：借码存字在别的机器上显示原日汉字，几个原厂假名组的候选被中文表占了位（最终版里 あ/さ 两组让位、し/は 已恢复）。对一个中文用户来说，这笔账划算。

**补记（2026-11-24）**：FT-5DR 合并版（SUB v6 + MAIN v8）已刷入真机并验收通过，あ/か/さ 入口、拼音序、末位可选按同一组锚点全部过关。2DR、3DR、5DR 三台的合并简体版至此全部闭环。
