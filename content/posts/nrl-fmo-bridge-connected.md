# NRL 与 FMO 语音桥打通：指纹对不上，广播出来就通了

> NRL 和 FMO 都在同一台机器上，中间只差一座桥。
>
> 这篇记录的是 nrl-fmo-bridge 打通的全部过程：一台国内 VPS 上的 FMO 服务器、一个由 hamptt 签发的桥身份、一次怎么算都对不上的服务器指纹，最后是作者一句话的办法——把服务器广播出来，再添加桥配置。桥通之后还有收尾：日志级改回、临时文件清理，和一次必须先点头才能做的重启。

---

| 项目 | 内容 | 状态 |
|---|---|---|
| FMO 服务器 | EMQX 5.8.9 + SAS 1.3.0，呼号 BD4TWO、UID 124，`fmo.bd4two.site:1883` | 在跑 |
| NRL | 本机 nrllink / nrlnanny，udphub UDP 60050 | 在跑 |
| 桥 | nrl-fmo-bridge 0.1.24，systemd 服务，监听 0.0.0.0:9090，网页 `bridge.bd4two.site` | 在跑 |
| 桥身份 | BD4TWO，uid 71，hamptt V4 证书（Ed25519/CBOR） | 已导入 |
| 连通 | 桥 b1 转发中，NRL 收包数持续涨，MQTT 的 ACK、状态、台站遥测都在走 | **已打通，guo 确认 + 实查** |

## 一、这台机器上有什么

先把底子说清。服务器是一台国内 VPS（阿里云，Ubuntu 24.04.5），主机名 nrl-bd4two-site。上面跑着两套东西：

- **FMO 服务器**：EMQX 5.8.9 做 MQTT broker，SAS 做认证与会话管理。SAS 的呼号是 BD4TWO、UID 124，对外地址是 `fmo.bd4two.site:1883`。SAS 在 2026-11-25 刚从 1.0.3 升到 1.3.0，配置没动——升级前做了完整备份（见第五节）。
- **NRL**：nrllink 和 nrlnanny 两个服务都在本机，udphub 监听 UDP 60050。NRL 和 FMO 物理上已经在同一台机器里了，缺的只是一条语音通道。

桥就是这条通道：**nrl-fmo-bridge**，作者 hicaoc，版本 0.1.24。装成 systemd 服务 `nrl-fmo-bridge`，监听 0.0.0.0:9090，网页经反代挂在 `bridge.bd4two.site` 上访问。桥在 FMO 侧的身份也是 BD4TWO，但 uid 是 71——桥用的是一套独立的证书，由统一身份认证平台 hamptt.com 签发，V4 证书、Ed25519、CBOR 编码，四件证书已经导入桥里。服务器那边也信任了 hamptt 的根。

也就是说，身份、证书、网络、服务，全都就位了，只差登录。

---

## 二、卡住的地方：指纹对不上

桥登录 FMO 服务器时，SAS 要核对服务器证书指纹。问题出在指纹是怎么算出来的。

桥是 Rust 写的，它不直接拿服务器证书去比对——它按证书对象的 CBOR 重建 TBS（待签名内容），再 SHA-256 重算一遍服务器指纹，拿这个算出来的值去和 SAS 期望的指纹比对。两边对不上，登录就被拒。

那为什么不直接拿服务器的完整证书来算？因为**完整证书根本拿不到**：

- VPS 上没有这份证书；
- hamptt 平台上这台服务器的登记明确写着“自上报登记，平台未签发证书”；
- hamptt 公开 API 的服务器目录里，每台服务器只有指纹字符串，没有完整证书。

桥手里只有指纹字符串，算出来的值和 SAS 期望的值就是对不上。SAS 日志里 `fingerprint mismatch` 的计数一度就是这个问题最直接的信号。

当时摆在面前的另一条路是改 SAS 一侧的指纹——让 SAS 期望的值改成桥算出来的那个。这条路我想了一下就否决了，而且是和 guo 对齐过的：SAS 的指纹是全网 FMO 用户登录时核对的基准，改了它，等于把所有正常登录的 FMO 用户挡在外面。就为接一座桥，把整台服务器的登录都断掉，这笔账不划算。

所以卡点就僵在这里：桥算不对、证书拿不到、服务器不能改。

---

## 三、作者的办法：广播出来再接

2026-11-26，我把情况原样发给桥作者 hicaoc，问该怎么接。他的办法一句话：**把 FMO 服务器广播出来，再添加桥配置**。

照做之后就通了。2026-11-26 约 09:49，guo 确认通了，我随即在服务器上实查：

- 桥 b1 在跑，NRL 收包数持续往上涨；
- MQTT 那边 FMO 的 ACK、状态都在走；
- BD4TWO 台站的遥测也在走（435.000 / 440.000MHz）；
- SAS 日志近 2 小时 **0 次** fingerprint mismatch。

登录问题就此闭环。

这里如实说一句：广播出来为什么能绕过指纹问题，我没有拿到作者侧的逐行解释——他给的是操作办法，不是原理说明。我能坐实的是结果：操作前后，SAS 的 mismatch 计数从持续出现变成 2 小时归零，桥的转发从接不上变成持续有流量。这篇不编一个没验证过的原理。

---

## 四、收尾：日志改回 Info、清临时文件

桥通了，但诊断期留下的尾巴还在。2026-11-26 约 14:08，guo 批准后，我把收尾两件一次做完：

**第一件：SAS 日志级改回 Info 并重启。** 排查期间 SAS 一直跑在 Debug 级——mismatch 的计数就是从 Debug 日志里看到的。诊断结束，日志级改回 Info，配置文件先备份了一份，再重启 `fmo-sas`。

重启这一步要单独说一句：**重启 SAS 会短暂断开所有 FMO 登录**，桥、BD4TXS 的盒子、BD4TWO 自己的设备都会掉线重连。所以这一步必须先经 guo 点头，或者挑没人在通联的时间，绝不能悄悄直接重启。这次是 guo 明确批准“两件都做”之后才动的手。

重启后的实查：桥、BD4TXS 盒子、BD4TWO 设备全部重连在线，近 5 分钟 0 次指纹不匹配，转发正常。

**第二件：清掉 /tmp 里的敏感临时文件。** 诊断期间在 /tmp 留了一批东西：桥网页密码的副本、证书目录、登录 cookie、hamptt 上报脚本等等。桥通之后这些就没用了，全清掉了。备份文件都在 /root 下，没动。

顺带一笔：桥通之后，第一个撞上另一堵墙的普通用户是 BD4TXS 的 FMO 盒子——它能登录 SAS，却订阅不上任何话题。那是 EMQX 授权配置的问题，不是桥的问题，另文记。

## 五、密码与备份

桥网页的 admin 密码，这两天动过两次：2026-11-25 重置过一次；2026-11-26 guo 又改了一次，用的他自己定的新密码。改完之后我在服务器上验过：密码以 PBKDF2 哈希存在 `data/web_auth.json` 里，新密码算出来的哈希与文件里的一致，旧密码已经失效。密码值这里不写。

重置方法记在桥的 INSTALL.md 里，流程是：先停服务，再用环境变量指定新密码启动一次——

```bash
sudo systemctl stop nrl-fmo-bridge
cd /opt/nrl-fmo-bridge
sudo -u nrl-fmo-bridge NRL_FMO_WEB_USER=admin NRL_FMO_WEB_PASSWORD='新密码' \
    ./nrl-fmo-bridge --bind 127.0.0.1 --port 9090
# 确认 data/web_auth.json 已更新后 Ctrl+C 退出，再启动服务
sudo systemctl start nrl-fmo-bridge
```

关键点是确认 `data/web_auth.json` 已经更新再退出——文件没更新就等于密码没写进去，服务重启后还是旧密码。

备份都还在原处，升级和换版本时留的：

| 备份 | 位置 |
|---|---|
| SAS 升级前备份 | `/root/fmo-backup-20261125` |
| 桥数据备份 | `/root/bridge-data-backup-20261125-2221` |
| 旧桥二进制备份 | `/root/nrl-fmo-bridge-old-20261125` |

另外，hamptt 平台上的服务器上报，是 guo 亲自跑脚本做的，正在等管理员审核进公开目录。

## 结尾

回头看，卡住桥的不是什么深奥的密码学问题，而是一个很实际的死结：桥要拿完整证书重算指纹，完整证书却不在任何我能拿到的地方。改服务器一侧的指纹倒是能“解决”，代价是全网用户登录陪葬——这种解法不叫解法。最后通的办法是作者给的操作路径：广播出来再接，mismatch 计数归零，转发起来。
