# 给 FT-710 做中文固件：破解 SFL 格式、自创双字节编码，与一次复检翻出的长度缺陷

> 手台那篇（[《解密八重洲手台固件》](https://blog.bd4two.eu.org/posts/yaesu-handheld-chinese-firmware/)）的打法是"借道"：EXP 固件里现成躺着日语槽位、双字节通路和汉字字库，改字符串、换字形就行。
>
> FT-710 没有这条道。这台机器的菜单字符串在一颗 CPU（MAIN）里、字体和渲染在另一颗（DISPLAY）里，DISPLAY 原生只会画单字节字符。中文得跨着两颗 CPU 造出来：先破解固件容器格式，再自创一套双字节编码、把 DISPLAY 的文本渲染函数重写掉，最后把 MAIN 的字符串逐条原位译掉。
>
> 而且这篇和手台那篇有一个根本区别：**手台的结论有真机照片背书，这一篇到发稿为止一个字节都没刷进真机**。所有结论都是文件级、模拟器级和审计级的，文中逐处标明。最后还有一章复检：构建交付之后，按手台 v1 翻车的教训把全部承重假设重新证了一遍——通道前提证住了，但翻出一个构建时漏掉的真实缺陷。

## 一、缘起：先纠正一个前提

起因是一句话：网上看到「IC-7300 有人用 AI 做出了中文固件」，问 FT-710 能不能照着搞。动手之前先查证这个前提，结论是它不成立：

- 真正被破解、能刷改的 Icom 是 **SQ6EMM 做的 IC-705 / IC-9700 / IC-905**；
- IC-7300 那个是 jeskko 的 homebrew，只在 QEMU 里跑，作者明说没上过真机；
- 「用 AI 做的」这个说法在 SQ6EMM 的仓库里找不到证据。AI 在这类工作里的真实位置是读反编译代码的助手——帮人更快看懂几千个函数，逆向、验证、担风险的还是人。

所以这件事的正确问法是：FT-710 的固件格式能不能解、界面文本在哪、刷坏了能不能救。和手台一样，先查这三样，再谈翻译。

机器本体是国行 FT-710，版本拍照确认：**MAIN V01-09 / DISPLAY V01-07 / DSP V01-01 / SDR V01-04，DST: CHINA**。比后面选定的构建基线（202402 包）旧一截，这个事实决定了刷机顺序里要先升官方版（第五章）。

## 二、架构：两颗 CPU，两个固件

FT-710 的界面是两颗 CPU 分工的（以下出自 reid-n0rc 的 FT-710 逆向文档与双方反编译互证）：

| 部件 | 芯片 | 管什么 |
|---|---|---|
| MAIN | Renesas RX651 | 射频与整机控制；**全部菜单字符串**存放在它的 ROM 表区；把屏幕内容打包成"帧"发给 DISPLAY |
| DISPLAY | RZ/A1H（Cortex-A9） | **字体与渲染**；收到帧后按固定偏移切分、逐字段绘制；固件升级界面本身也跑在它上面 |

帧协议：MAIN 的 SCIF5 ↔ DISPLAY 的 SCI1，约 340.9 kbit/s、8 数据位、2 停止位、无校验、无流控；帧格式 `[类型字节][载荷][8 位累加和校验]`，停等应答（ACK/NAK，30 ms 超时 × 3 次重试），内容无变化的帧不重发。各帧前 0x97 字节是整机状态块，自有载荷从 0x98 起。主菜单页是帧 0x40，总长 0x1FB 字节：P1 标题 20 B、8 个 P2 页签 × 13 B、5 行条目（每行步长 45 B：条目名 21 B + 值 21 B + 标志与长度字节）。

MAIN 侧字符串的存储规律是决定性的：**全部是定长、空格右填充、无 NUL、无长度前缀、无指针表的密集数组**，代码按「表基址 + 序号 × 步长」取用。推论：替换只能原位、同宽——任何改长度都会错位其后全部字段。好消息是中文一般比英文短，宽度普遍够用。

与手台路线的根本不同，在 DISPLAY 的渲染方式：

- 手台 SUB 原生支持双字节（日文就是双字节画出来的），字库里有 6,485 个汉字字形，缺的简体字换字形即可，**渲染代码一行不用动**；
- FT-710 的 DISPLAY 只有一个单字节渲染器 `gui_draw_text`：逐字节查一张 256 字节的字符映射表（cmap）得到字形下标，再取预着色的 run sprite 点阵绘制。映射表里高字节几乎全是空白（详见第七章的字节空间审计）——**没有任何现成的双字节通路**。

所以这台的工作清单是三件：DISPLAY 侧自创双字节编码 + 改渲染器 + 建中文字库；MAIN 侧按定长合同逐条译字符串；两边共用同一份码表作为唯一事实源。MAIN 侧不需要改协议、不需要改代码——它照旧复制同样的固定字节数，解码与推进全在 DISPLAY 补丁里完成（这条推论当时标为 [inference]，第八章复检时被代码证据坐实）。

## 三、SFL 格式破解：可写的前提

两个固件都是 `.SFL` 文件。工具链来自 Nikolay-Kha 的 ft710-internals（`decode_sfl.py`），格式细节与 reid 的逆向文档交叉核对。

### 3.1 容器结构

- 首行是文本头：`FT-710_MAIN_V0112.SFL MC B092FD93`——文件名、类型 tag（MAIN 是 `MC`，DISPLAY 是 `PC`）、一个校验 token；
- 其后是经 **43 字节替代表混淆**的 Motorola S-record 文本。MAIN 与 DISPLAY 的唯一区别是混淆计数器：MAIN 逐行加密（T5 行 counter=17、普通数据行 counter=0），DISPLAY 是连续流 counter=0。

### 3.2 完整性校验：只有加盐 CRC-32，没有签名

校验公式实测为：

```
zlib.crc32(SALT, zlib.crc32(enc_payload))，SALT = 0x139EECA6（小端字节 A6 EC 9E 13）
```

作用于**加密后的载荷**，结果与首行第三个 token 比对。更关键的是 DISPLAY 侧读取函数 `sfl_read_header` 的行为：**只比对 CRC，tag 和长度字段都不查**。整个格式里没有任何签名。这意味着：改完内容、用同一公式重算 CRC，文件在格式层就是合法的——可写的前提成立。

工具链往返实测：`decode_sfl.py verify` 对原厂 MAIN 在 non-rebuild 与 rebuild 两条路径均 PASS（解包 → 原样重打包 → 校验通过，未改一字节语义）。MAIN 解出 28,229 条 S-record（逐条校验和全 OK）、451,462 字节数据、17 个块，入口 0xFFF8FBDB。DISPLAY V01-08 解包 3,324,944 字节，回打包 round-trip 同样 PASS。

### 3.3 两个旁证

- MAIN 的 option-setting 区（0xFE7F5D00 起）解出来**全 0xFF**：没有 ID 保护、没有写保护位。注意重打包时这些区域的危险位必须保持原样，不要"顺手优化"。
- 已有真机先例：MARS/CAP mod 对这同一个 MAIN 文件做过 5 字节补丁（区域码函数）+ 修正首行 CRC 并在真机刷入成功（DST 变 DEV）。MAIN 可补丁不是理论推测。

## 四、先查恢复，再动手

这是这个项目定的纪律，顺序不能反：**恢复路径没查清之前，不许谈刷机**。而且这一章本身就有一个先错后改的过程，如实记录。

### 4.1 最初的担心，和它的推翻

最初的判断是悲观的：DISPLAY 固件里跑着固件升级界面本身——刷 DISPLAY 的程序就在 DISPLAY 里，万一 DISPLAY 改坏，谁来把它刷回来？当时一度下了"DISPLAY 是刷写者本身、改坏了没救"的结论。

查完 reid 的更新流程文档后，这个担心被推翻，证据有四层：

1. **双 bank**：DISPLAY 闪存分两个 bank，每 bank 6 MiB，现镜像只用 3.3 MiB。更新写的是另一个 bank，新 bank 的标志写好之前旧 bank 不动；
2. **启动不查镜像 CRC**：启动只看 bank 标志 {0x11111111, 长度 ≠ 0} 选 bank，不校验镜像内容——刷进去的镜像哪怕逻辑全错，也不会卡在"校验不过不让进恢复"这种死局；
3. **BOOT LOADER 维护屏独立于 bank 镜像**：它住在 loader 区，不随 bank 镜像走。进入方式：关机按住 **DNR + A/B + QMB** 开机，转动主调谐旋钮净步数超过 4 步解锁。DISPLAY 镜像起不来时，可以从维护屏重刷官方 DISPLAY；
4. **J6003 ARM JTAG 口**在主板上，是最后一层硬件兜底。

### 4.2 MAIN 的恢复：刷写者根本不是 MAIN 自己

MAIN 刷坏的恢复证据链更完整，四条互相独立：

1. **DISPLAY 侧有专门的 MAIN 恢复屏**：MAIN 无应答时，DISPLAY 的 `fwupdate_screen` 进入两步恢复流程，要求 SD 卡上 MAIN 与 DISPLAY 两个文件都 Ready，**先刷 MAIN（STEP 1 of 2）、再刷 DISPLAY（STEP 2 of 2）**；
2. **刷 MAIN 的执行者是 DISPLAY**：它通过 RX651 的**串行 boot ROM**（SCI1 + RX_UPDATE/RX_RESET 控制线）给 MAIN 烧录，ID 码 16 × 0xFF（无保护），逐区写入后读回比对。**MAIN 固件哪怕完全不启动，也不影响重刷 MAIN**；
3. **八重洲官方手册自己承诺**：升级手册的 Caution 原文——更新被中断导致机器不能正常工作时，"follow the instructions on the screen, and start again from step 1"（第 6 页与第 9 页各一份）；
4. **硬件兜底**：主板 J1004「RX-CPU DEBUG」引出 Renesas FINE 调试与 SCI1 boot 模式，E2 Lite 或 3.3 V USB-UART 即可给空白 MAIN 重刷。

### 4.3 分级与纪律

把话说全：以上恢复机制都是**代码与文档层查证的 [fact]**（函数、流程、手册原文都在），但**没有一条在这台机器上实机演练过**——"照文档操作就能救回来"这一步是 [inference]。这和手台那篇的恢复标注是同一口径。

由此定下的纪律只有一条，但贯穿全程：**DISPLAY 与 MAIN 永远分开刷、分开验，绝不同时动**。风险不在"刷坏一个"，而在"同时刷坏两个"；逐个验证就把风险关在笼子里。SD 卡上常备原厂 MAIN + DISPLAY 两个 SFL（恢复屏要求两个都 Ready）。

## 五、基线：先升官方 202402

全部构建的地址与偏移都绑定在官方 202402 包上（MAIN V01-12 / DISPLAY V01-08），版本绑死，八重洲出新固件要整套重移植。本机当时是 MAIN V01-09 / DISPLAY V01-07，所以刷自制件之前的固定前置是：

1. 先把电台设置备份到 SD 卡；
2. 按官方手册顺序升 202402：**先 DISPLAY、后 MAIN**（顺序错了同样按手册"从 step 1 重来"处理）；
3. 升完确认 SOFT VERSION 显示 MAIN V01-12 / DISPLAY V01-08，且 **DST 仍为 CHINA**。

两个定心丸：DST 是机器硬件配置决定的，官方包全球同一个文件，刷官方包不会变区域；DSP V01-01 / SDR V01-04 本来就是最新版，不用动。

## 六、小样 v1：8 个字形 + 1 条字符串

全量动手之前先做小样，目的只有一个：在**不改代码、不改 .data2、不追加任何数据**的前提下，证明"改过的 DISPLAY 镜像能被电台接受、改过的字形能被画出来、维护屏恢复入口真实存在"。方案是原位替换：挑 8 个没人用的字符，把它们的字形 sprite 原位换成汉字，再把一条字符串原位改成由这 8 个字符拼出的句子。

### 6.1 目标字符串与一处假设纠正

目标选维护模式引导屏的标题：VA `0x204280BC` 的 `"YAESU FT-710 BOOT LOADER V01-02"`。选它是因为看效果不用再刷机——刷完进一次维护屏就能看到，且它没有任何 strcmp 引用，改内容不影响逻辑。

最初假设它由引导屏的 12×18 字体表绘制。查反编译后结论是**不是**：标题在三处绘制点（`fwupdate_menu_screen`、更新进度屏、`fwupdate_select_draw`）全部使用 **15×24 主字体表 `0x20800CAC`**，12×18 表画的是入口屏的其他字符串。目标字符串不变，换的是要改的字体表——假设错了就改，特此记录。连带影响：这张 15×24 表也供 MAIN 菜单与列表使用，小样的捐献字符若出现在菜单文本或 SD 卡文件名里，那些位置会显示成汉字（纯外观，无功能影响）。

### 6.2 捐献字符

渲染路径是 `gui_draw_text` 逐字节查 cmap（VA `0x2080173C`）得字形下标，再取 sprite 绘制。映射规律：`0x21–0x5F` → 下标 = 字节 − 0x1E；`0x61–0x7D` → 下标 67–95；`0x80` → 96；`0xFE` → 97。两个陷阱先排除：反引号（0x60）和 `~`（0x7E）都映射到下标 2，而下标 2 是 NULL（空格），不能当捐献字节。

盘点引导/更新屏全部字符串后，未被使用的可打印字符里挑出 8 个捐献位，按"字越大配越大的位"贪心分配：

| 汉字 | 捐献字节 | runs | pixels | 需要 / 可用（字节） |
|---|---|---|---|---|
| 测 | `&` | 49 | 58 | 312 / 528 |
| 固 | `$` | 30 | 64 | 248 / 436 |
| 成 | `q` | 32 | 47 | 222 / 352 |
| 试 | 0x80 | 28 | 45 | 202 / 352 |
| 功 | `z` | 27 | 39 | 186 / 280 |
| 件 | `j` | 25 | 39 | 178 / 228 |
| 中 | `{` | 17 | 37 | 142 / 228 |
| 文 | `<` | 18 | 34 | 140 / 216 |

字形来源是 Fusion Pixel Font 12px zh_hans（OFL 协议）：原生 12px 渲染二值化，11×11 墨迹放进 15×24 字格的 (1,6) 偏移，单色 0xFFFF。选像素字体是算过账的：矢量字体（Noto Sans SC）在这个尺寸抗锯齿再二值化，最复杂的「测」要 500+ 字节，捐献位装不下；像素字笔画干净、run 数少，8 个字全部装得下还有余量。字节 0x80 放进字符串的安全性单独核过：分词分隔符只有空格，isspace 判断只覆盖 0x09–0x0D 与 0x20，它不会被当成终止符或分隔符。

新标题的确切字节（原 32 字节字段原位改写，前 16 字节有效）：

```
7B 3C 24 6A 26 80 71 7A 20 46 54 2D 37 31 30 00
 {  <  $  j  &  .  q  z     F  T  -  7  1  0 \0
 中 文 固 件 测 试 成 功  「 FT-710」
```

### 6.3 验证与看效果的方法

- 与原厂逐字节 diff：共 **1,859 字节**不同，全部落在 9 个区间内（8 个字形区 + 标题字段），脚本断言 PASS，无一例外；
- `decode_sfl.py verify`：non-rebuild 与 rebuild 两条 round-trip 均 PASS；SFL 头与原厂相比只有 8 个 CRC 数字不同，盐化 CRC 已重算；
- 用固件自身的 sprite 模型（`display_assets.py --render`）对成品载荷逐个渲染 8 个新字形：可辨认，「中文固件测试成功」按序成形；
- 产物 `FT-710_DISPLAY_V0109.SFL`，SHA256 `77e77401…`。文件名不是随手起的：电台只认 `FT-710_DISPLAY_V` + 任意 4 字符 + `.SFL` 的等长模式，`0109` 显示为版本「01-09」、高于已装的 01-08 会被预勾选；归档用的长文件名（`…_CN_POC.SFL`）不符合模式，拷上去电台会当它不存在。

看效果：关机按住 DNR + A/B + QMB 开机，转主旋钮净步数 >4 解锁，标题应变为「**中文固件测试成功 FT-710**」（11×11 像素字在字格中央，比旁边的拉丁字母小一圈，是预期效果）。**警告：看完关机，不要在解锁的维护屏上发起 DISPLAY 更新**——解锁后 boot-info 被置为 loader 模式，从此屏发起的更新会写 loader 区而不是普通 bank；刷机只走正常菜单 `SETUP → SD CARD → FIRMWARE UPDATE`。恢复就是同法刷回官方 V0108。

状态如实：小样只做到了文件级验证，**未上真机**；后来全量方案里它被探针（下一章）取代，最终没有刷它。

## 七、全量构建：编码、渲染器、字库、翻译

全量方案的设计文档是 `DISPLAY_CN_DESIGN.md`，构建分四段：Stage 0 反汇编复核 → Stage 1 探针 → Stage 2 翻译 → Stage 3 全量。这一章按部件讲。

### 7.1 自创双字节编码

编码定义：

```
lead  ∈ [0x81, 0xFD]                      （125 个）
trail ∈ [0x40, 0x7E] ∪ [0x80, 0xFC]       （63 + 125 = 188 个）
code_index = (lead − 0x81) × 188 + trail_index    （0..23499）
```

构建时把字符集排序后顺序分配 code_index（稠密私有码表），字节对由 index 反推。为什么 lead 选这个范围，是对着 cmap 做完字节空间审计的结果 [fact]：stock 固件里 `0x81–0xFD` 全部映射到空白字形 2——这 125 个字节值画不出任何东西；只有三个高字节有真实字形：0x80（Ω 形符号）、0xFE（⏎ 状箭头）、0xFF，都保留 stock 单字节语义，不进 lead 区间。文本生产者也全审过：DISPLAY 自有字符串、MAIN 菜单大表全部纯 ASCII（.data2 里的键盘布局数据含高字节，但不走文本绘制；文本终端视图用自己的渲染器）。

编码的每条性质都是刻意选的：

- **无 0x00**：编码串仍是合法 C 字符串，strlen/strcpy 语义不破；
- **无 0x20**：按空格分词的绘制器不会把汉字从中间劈开，MAIN 的空格填充也不会被误认成 trail；
- **无 0x0A/0x0D**：帧里 LF/CR 有行标记语义，不占用；
- **trail 避开控制区**：不触发 isspace 类判断；
- **悬空 lead 安全**：lead 落在字符串末尾（后跟 NUL）时 trail 非法，渲染补丁回退为单字节空白绘制、只进 1 字节，绝不越界读。

### 7.2 渲染器补丁：改 4 个字

动手前先纠正一个预设：`gui_draw_text`（`0x20135DD4`，108 字节）是 **ARM 状态（A32）代码，不是 Thumb**——入口字 `0xE92D5FFF` 是 `STMFD sp!, {r0-r12, lr}`。反而更好：指令定长 4 字节，B 跳转范围 ±32 MB 整 bank 可达，无状态切换问题。

补丁本体只改原镜像 4 个字：

1. **入口跳转**：`gui_draw_text` 入口的 `STMFD` 一个字 → `B cave_draw_text`，跳到镜像尾部追加区的新实现。新实现完整复刻 stock 语义（纯 ASCII 输入时 cell 恒等于字节下标，含 x 的 16 位回绕，与 stock **逐像素一致**），只多一条分支：遇 lead byte 且 trail 合法、index 在字库范围内时，从中文表取描述符绘制并进 2 字节；其余一律走 stock 的 cmap 路径。它只调用 `gui_draw_runs`（同为 ARM 代码，BL 直达），不碰 Thumb 库函数。体积约 380 字节（含字面量）。
2. **三处 strlen 改 cell 计数**：只改绘制函数不够——两个测量助手（`gui_draw_text_words`、`gui_draw_text_centered`）用 strlen 算步进与宽度，含汉字的串会被算宽。新增 `text_cells(str)`（追加区，按同一 lead/trail 规则数"字"数，纯 ASCII 时与 strlen 恒等），把三处步进/宽度用途的 `BLX strlen` 改成 `BL text_cells`。
3. **另三处 strlen 故意保留**：一处是 memcpy 长度（必须按字节）；两处是居中函数里数空格的循环边界——本码表 trail 永不为 0x20，按字节数空格不会误计汉字。改错任何一处的后果是截断拷贝或算错步进，所以这 6 个调用点在 Stage 0 用 Capstone 逐条解码、逐条对上下文确认用途，无一出入。

**.data2 与 cmap 一字不改**：补丁在查映射表**之前**分支，lead byte 根本不进 cmap，stock 映射表与全部 stock 字体指针表原样保留。设计阶段还顺手做了一个原型证明：自写的贪心 LZ 编码器能把 stock 的 .data2 重压缩到 12,661 字节 ≤ 可用 span 12,752（比 stock 自己的 12,751 还小 90），解压逐字节一致——将来若要动 .data2 有路可走，但 v1 不需要动它（纯字面量编码要 36,215 字节，装不下，"纯字面量可接受"的初始假设是被这个原型否定的）。

### 7.3 字库：共享像素池

新字形全部放镜像尾部追加区：稠密指针表 + 描述符/runs 数据 + 共享像素池。镜像是定址 XIP 布局，全部指针是绝对 VA（= 0x20100000 + 文件偏移），构建时把表基址与字数 K 写进补丁代码即可，无重定位问题。

关键优化是**共享像素池**：中文字形是单色，像素数据就是同一个 u16 重复 P 次。反编译证实 `gui_draw_runs` 按描述符的 runs_ptr / pix_ptr 独立取数据，并不要求 pix_ptr 紧跟 runs——每种颜色只需一个 ≥ 最大像素数的共享池（实测最大字形 77 像素，池预留 512 B），每字省掉全部像素字节：

| 方案 | 每字字节 | 800 字总量 |
|---|---|---|
| stock 式独立像素 | ≈233 | ≈185 KB |
| **共享像素池** | **≈134** | **≈107 KB** |

需要中文字形的只有 **15×24** 一种字号（帧 0x40 与 0x62 的全部文本），颜色两套：白（两个白色字体表主色同为 0xFFFF，共用一套）+ 橙（高亮值字体 0x20800E34，主色 0xFF80）。24×36 滑杆值是数字/单位不译；38×42 值弹窗不备字形，汉字到那条路径时按设计回退画 15×24 白字（偏小、能读）。

字符集怎么定有一条硬教训：**不能按 GB2312 频率前缀截断**。实测菜单核心词的 GB2312 序位散布极广——菜 230、设 2421、显 2965、语 3368、置 3606，"取前 800 个常用字"会直接漏掉设、置、显、语。正确做法是先完成全部翻译、取译文实际用到的汉字全集，并入少量预备字；构建时对未分配字符**报错中断**，绝不静默出空白字。

### 7.4 探针 V0110：为最大的未知数而设

追加区方案有一个静态分析证不死的未知数：stock 镜像只用到 bank 前 3.17 MiB，"XIP 窗口覆盖整个 6 MiB bank"没有直接证据（详见第八章）。探针就是为退掉这条风险设计的最小长镜像：

- 构造：stock DISPLAY + 4 个补丁字 + 追加区 9,205 B（洞穴代码 380 B + 32 字 × 2 色字库 + 共享像素池）+ 引导标题改用**新双字节编码**写「中文菜单测试 FT-710」；
- 验证点：正常开机进主界面（追加区可读/可执行）→ ASCII 显示无异 → 进维护屏看标题。标题若正确显示，等于同时证明：追加区的代码能被取指执行、字库数据能被取数、洞穴渲染器端到端工作；
- 文件级验证：`decode_sfl verify` 两条 round-trip PASS；解包载荷与构建镜像逐字节相同；与 stock 的 diff 只落在 {入口字、3 个 strlen 字、标题 32 B 字段、追加区} 内，断言 PASS。

探针与全量的差别只有长度（全量多约 54 KB），两者之间不存在任何已知的架构边界（下一边界是 6 MiB bank 末端）——但严格说，探针证的是机制，全量多出的跨度仍是同机制的外推，第八章复检保留了这一层表述。

### 7.5 全量 DISPLAY V0111

- 追加区 63,044 B：代码 380 B + **249 字 × 2 色字库**（共享像素池；最大字形 77 px ≤ 池容量）；新镜像 3,387,988 B，距 6 MiB bank 上限余量充足（构建软上限设 5.5 MB）；
- `decode_sfl verify` PASS；解包与构建镜像全等；与 stock 的 diff 在 stock 长度内只有 6 个小区间（4 个补丁字 + 标题字段等），全量字库都在追加区；
- 哈希 `cf6e1e92…`，大小 3,388,564 B。

### 7.6 MAIN V0113：483 处原位译

翻译范围是核心集合：782 条字符串出现、510 个去重文本。译 **284 个去重文本 → 483 条出现被改写**；其余 226 个按政策保留 ASCII：纯数字/单位标签（`100Hz`、`  4800bps`…）、业余无线电惯用缩写（AGC、USB、MIC、QMB…）、格式码（`12NO`、`A2NT`…）与哨兵（`DONE` 不译）。语言名译为中文（`葡萄牙语(巴西)` 等），月份当时译为 `1月`…`12月`——记住这条，第八章要回来找它。

翻译合同（MAIN_ANALYSIS 给 DISPLAY 侧定的字节合同）：

1. **字节预算即格预算**：汉字 2 字节/格。标题 ≤20 B、页签 ≤13 B、条目名 ≤21 B、值 ≤21 B、纯文本行 ≤30 B、0x62 名称 ≤20 B、0x62 值只有 3 B 基本只能留 ASCII；
2. 填充一律 0x20；`DONE` 哨兵保持 ASCII；标志字节语义不动；
3. 页签名不内嵌空格（分词绘制会错位）。

构建结果：**拟合例外 0**——全部译文在双字节编码下 ≤ 字段宽度，最紧的是 `MODE PSK/DATA` → `PSK/数据模式`（12/13 B）。字符集 = 全部译文汉字 ∪ 标题字 = **249 字**，按码点排序稠密分配，即 DISPLAY 与 MAIN 共用的 `codepage.tsv`。MAIN 构建路径：S-record 解析 → 字节映射（与分析阶段的平坦镜像交叉核对 0 不一致）→ 按译表逐字段原位写入（编码 + 空格补齐、同宽）→ 记录结构不变地重组 → `pack --rebuild`。验证：verify PASS；与原厂 diff 共 **4,528 字节，全部落在 483 个被译字段内**（断言 PASS）——表大小/步长/顺序、代码、option 区、区域数据一字节未动；随机抽 6 个字段从成品 SFL 解码回读，与译文全等（如 `DISPLAY SETTING` → `显示设置`）；成品与原厂同为 1,355,160 字节，原位替换的必然结果。

### 7.7 模拟器验证：验了什么，没验什么

这一节必须分开写，因为两者经常被混为一谈。

**启动模拟**（reid 的 `display_boot_emu.py`，Unicorn 全系统启动，8,000 万条指令）：stock、探针、全量三个镜像的启动报告**逐项相同**——SVC 115,929 次、IRQ 1,500 次、33 个任务、task_root 与 gui_main_loop 均到达、无 fault。结论：长镜像在该机器模型里能正常启动到 GUI 主循环。

**但启动模拟证明不了渲染**。诚实边界是构建方自己做控制实验挖出来的：该模拟器不连接 MAIN 就没有文本帧，80M 指令内 `gui_draw_text / words / centered` 的入口计数为 **0**——启动模拟里渲染器根本没被调用过。所以渲染正确性由下面的直调差分单独证明，不能由启动模拟代替。

**渲染器直调差分**（Unicorn 直接调用三个绘制函数与 text_cells，同机状态对比 stock 与补丁版的帧缓冲与 RAM 演化），全部 PASS，要点：

- 13 个 ASCII 用例（三种绘制路径 × 白/菜单/橙字体、滑杆 24×36 字体、空串、贴边坐标、0x80/0xFE/0xFF 旧高字节字形）：结果状态、帧缓冲、RAM 演化与 stock **逐字节相同**；
- stock 的既有怪癖原样保留：某字体表的空白字形指针为 NULL，用它画空格在模拟器里 fault——stock 与补丁版 fault 方式一致，不是补丁引入的回归（真实菜单该字体字段不含空格）；
- text_cells 11 个用例与设计参考实现全对（含非法 trail、末尾悬空 lead、0xFD/0xFC 边界）；
- 中文路径：标题在白/橙两色下与构建位图**逐像素一致**（各 277 px）；全量版另验真实菜单串——`AGC慢延迟`、`CAT-1超时定时器`（分词路径）、`PSK/数据模式`（居中路径，落点由 text_cells 宽度公式决定）、`外置天调`（居中、全字像素全等）、`葡萄牙语(巴西)`（橙色值字体）——中文像素全部与构建位图逐像素一致。

### 7.8 已知覆盖边界（v1 范围，不是缺陷）

- 帧 0x62 校准（alignment）标签 261 条未译（工厂校准屏，多为缩写 + 数字）；
- DISPLAY 自有字符串（引导/更新屏、SD 菜单等）除引导标题外仍英文；编码与渲染已支持，后续可增量译；
- 值弹窗（帧 0x31，38×42）与滑杆值（24×36）不备中文字形，按设计回退 15×24 白字；
- 软键标签、运行时标签、信道列表标题等次要集合未译。

## 八、复检：按手台的教训，把承重假设重新证一遍

构建交付之后没有立刻刷机，而是先做了一轮独立复检。动因正是手台那篇第三节的教训：**v1 的文件级检查全过，错的是"译的那张表就是屏幕真正读的那张"这个通道前提**——diff 审计再干净也证明不了通道归属。FT-710 这套构建同样压着几条承重假设，复检的要求是：每条都必须从代码/数据流**证明**，不接受推定。

### 8.1 方法与限制（先说清）

- 全部复检使用审计方**自写工具**：按格式规格独立重写的 SFL 编解码器、S-record 解析、diff 审计、长度常数提取脚本，以及自装的 Capstone 5.0.9 做 ARM 反汇编。自写编码器先用"重编码官方 stock 与 V0113 两个文件均逐字节复现"验证过，解码结果与工程记录的解包产物逐字节一致——审计工具本身先过往返关，再用它审别人；
- **限制（明示）**：复检期间工作区代码处于禁执行状态，工程自带的 `decode_sfl.py verify` 与 Unicorn 模拟器差分**未能重跑**，其结论只能引用构建时的记录日志，不算本次独立复现。本章标 [本次实证] 的都是审计方独立重算/反汇编所得；标 [引用记录] 的来自构建日志与 reid 文档。

### 8.2 通道前提：证住了，而且和 3DR 正好相反

最怕的那种翻车——译错存储——在 FT-710 上被逐项排除 [本次实证]：

- **帧里装的是原样字符串，不是索引**：FUNC 菜单全部文本由 MAIN 序列化进帧 0x40/0x62/0x70，DISPLAY 按固定偏移切分绘制（双方反编译互证）。翻译落在 MAIN 的字符串字段里，就是显示路径的源头；
- **无第二存储**：对 stock MAIN 做全镜像猎查，483 个被译字段的样本串在其他位置的重复出现，全部落在同一张表内部（条目本身跨组重复，如 TIME OUT TIMER ×9、AGC SLOW DELAY ×10 都在菜单名表跨度内）；stock DISPLAY 解码镜像中 MAIN 菜单串的副本数为 **0**——DISPLAY 只有自己的 FIRMWARE UPDATE、SD CARD、BOOT LOADER 等原生串；
- **无影子语言表**：stock MAIN 七个被译表区间（对话框、消息标题、P1、P2、值表两段、菜单名）内 ≥0x80 的字节数**全为 0**，不存在日文/他语言影子表。**手台 v1 翻车的那种结构，在 FT-710 上不存在**——这台根本没有第二语言，七张表就是唯一的表。ROM 里其他高字节集中区是校准数据，不是文本；
- **代码确实从这些字段取串**：每张被译表的基址都以字面量出现在 MAIN 代码中（菜单名基址字面量在 0xFFFD538D；P1/P2 在 0xFFFC9A1A / 0xFFFC9A77；值表第一段被引用 4 次、第二段 2 次）。

DISPLAY 渲染补丁也在最终二进制上逐项复核 [本次实证]：4 个补丁字全部正确（入口跳转的实际指令字解码目标无误；设计文档里的指令字是示意值，文档本身注明构建时重算）；绘制链完整——标题/值走 centered → words → 补丁入口，页签/条目名走 words，纯文本行与 0x62 帧直达补丁入口，全镜像直调补丁入口共 74 处；**没有旁路绘制器能收到汉字**：右对齐绘制器 FUN_20135E40 全镜像调用点为 0（死代码）；文本终端渲染器只喂调试 ASCII 流；键盘绘制器只被键盘屏调用、输入域是它自己的 ASCII 按键网格；其余约 290 处 `gui_draw_runs` 直调是图标/控件的固定字形绘制，不处理字符串。洞穴代码 380 字节逐条反汇编与设计伪码逐项吻合（寄存器契约、lead/trail 判定、索引公式、越界回退、橙/白选表、x 回绕全对）；白/橙两张中文字体指针表各 249 项**全部非零、0 个指向追加区之外**；MAIN 侧 483 个字段用码表解码回读与译表**全等**。

Diff 审计从零重跑 [本次实证]：三件交付物的盐化 CRC 全部吻合、声明大小与文件大小一致、SHA256 与构建报告逐一吻合；MAIN V0113 vs 原厂 V0112 总改动恰 **4,528 字节，落在 483 个被译字段之外的改动 = 0**，字段尾填充全为 0x20；DISPLAY 在 stock 长度内的 diff 恰为 6 个区间，追加区 +9,205 / +63,044 B 与构建报告一致。基线锁也顺带证实：三件交付物确实都是在官方 202402 的解码产物上改出来的，改动集严丝合缝，不存在基线错位。

### 8.3 真正翻出来的缺陷：值长度字节

通道没错，渲染没错，缺陷在一条更细的合同上——**帧 0x40 每行的值长度字节**。

先看这条合同在构建阶段的认知：MAIN 分析文档早就记下了它的存在——行首第 2 字节是"值文本字节数（& 0x1F），由 on_draw 给出"；构建报告的风险节也专门点了它（"按字节处理、无妨"的结论 + 提醒真机抽查最长的值标签）。翻译侧的拟合检查核的是**字段宽度**：全部译文 ≤21 B，例外为 0。看起来万无一失。

复检把语义挖到底，事实是另一回事 [本次实证]：

- **长度字节不是按字符串算出来的，是每个 on_draw 函数里写死的常数**（反编译实证，如 `menu_draw_lcut_slope` 写 `param_1[1] = 8`、`menu_draw_hcut_freq` 写 `= 6`；全镜像约百处）。这个常数恰好等于该条目**英文**标签的最大字节数；
- **DISPLAY 只按这个长度取文本**：`scr_text_list` 的三种行渲染路径都按 `memcpy(dst, row+0x18, *(byte*)(row+1) & 0x1F)` + `str_rtrim` 消费它。中文编码比常数长时，**超出部分根本到不了屏幕**；更糟的是截断点可能落在一个双字节字的中间——洞穴渲染器对悬空 lead 回退画空白，不崩，但显示是错的；
- 也就是说，真正的约束从来不是 21 B 的字段宽度，而是每个条目各自的英文长度常数。构建时的拟合检查核错了对象——它核的是"装不装得进字段"，没人逐条核"过不过得了长度字节"。构建报告其实嗅到了这条风险（MAIN 分析里称它"最可能的实际坑"），但只停在提醒，没有执行逐条目交叉核对。**这正是复检补上的检查。**

检查方法：从反编译中提取全部值标签的管辖函数与常数（约 60 个标签组，含两种指针写法：字面量 + 索引 ×0x15 + 偏移，以及相对值表基址的写法），再与 104 个已译值字段逐一比对——**命中 11 个超限字段**：

| 字段 | 原文 → V0113 译文（字节） | 长度常数 L | 若刷 V0113 的后果 | V0114 改法（字节） |
|---|---|---|---|---|
| 0xFFF83826 | REAR → 后面板（6） | 4 | 只显示「后面」，词义错误 | 后置（4） |
| 0xFFF84A5C | REAR → 后面板（6） | 4 | 同上 | 后置（4） |
| 0xFFF83CD3 | ENC → 编码（4） | 3 | 「编」+ 半个「码」字（悬空 lead） | 编（2） |
| 0xFFF841D4 | NOR → 正常（4） | 3 | 「正」+ 悬空 lead | 正（2） |
| 0xFFF841E9 | REV → 反向（4） | 3 | 「反」+ 悬空 lead | 反（2） |
| 0xFFF8438D | NOR → 正常（4） | 3 | 同上 | 正（2） |
| 0xFFF843A2 | REV → 反向（4） | 3 | 同上 | 反（2） |
| 0xFFF8451C | INT(FAST) → 内置(快速)（10） | 9 | 缺右括号 | 内置快速（8） |
| 0xFFF84EF4 | OCT → 10月（4） | 3 | 「10」+ 悬空 lead | 回退 OCT（3） |
| 0xFFF84F09 | NOV → 11月（4） | 3 | 「11」+ 悬空 lead | 回退 NOV（3） |
| 0xFFF84F1E | DEC → 12月（4） | 3 | 「12」+ 悬空 lead | 回退 DEC（3） |

11 个里 8 个会劈开双字节字。这就是第七章埋的那条线：月份译文 `10月/11月/12月` 每个 4 字节，而它们的常数是 3。

### 8.4 修复 V0114：只改字符串，不碰代码常数

修复决策的原则是**零代码风险、可完全静态验证**：

- 能改短的全在字符串侧改短：后置 / 编 / 正 / 反 / 内置快速——均为本组内自洽的紧凑中文（正/反同组的另两值"半/全"本就是单字译法；编与同组未译的 OFF/TSQ 并列无碍）。新字全部取自现有 249 字码表，DISPLAY 无需改动；
- 月份三项在 3 字节内**不存在任何中文写法**（「10月」4 字节，「十月」也是 4 字节），只能回退英文缩写 OCT/NOV/DEC；1月–9月是 3 字节，保留中文；
- 备选方案是把 `menu_m4_16_1_draw` 的常数 3 改成 4，只需改 1 个代码字节——**没有采用**。理由写清楚：审计尝试用差分法在 34 个同尺寸 on_draw 函数间定位该立即数，未找到一致的字节位置（审计环境无 RX 反汇编器可用），达不到可验证标准。为三个月份标签去冒改错一条指令的风险，不值得。此项留作**开放问题**：日后若有 RX 反汇编手段且能确证字节位置，可单独发一版把 12 个月份全恢复中文。

V0114 的构建方式：在 V0113 的解码产物上仅替换上述 11 个字段，重算受影响的 14 条 S-record 校验和与文件头盐化 CRC，其余字节（含官方头注释框）与 V0113 逐字节相同，文件大小不变（1,355,160 B）。复验 [本次实证]：盐化 CRC 吻合；28,229 条记录校验和错误 0；vs 原厂改动 4,506 字节、**全部在 483 个字段内**；vs V0113 恰差 **36 字节、全部在 11 个修复字段内**；11 个字段回读与预期逐字一致；长度常数审计重跑 **0 超限**。译表 `translation.tsv` 已同步更新这 11 行，重建不会再引入该缺陷；构建报告末尾已加作废附记。

**结论：MAIN V0113 作废，不要刷；刷 MAIN 只刷 V0114。** 探针 V0110 与 DISPLAY V0111 复检无恙，原样成立。

### 8.5 追加区 / XIP：仍是 supported-but-unproven

复检没有改变这条的定级。支持它的静态事实 [引用记录]：DISPLAY 更新器对文件只有两项检查（大小 ≥ 0x242、解码字节数 == 文件大小 − 0x240），对 6 MiB bank **无上限检查**，按载荷长度擦除/写入；启动不查镜像 CRC，bank 标志 {0x11111111, 长度 ≠ 0} 即选 bank；stock 镜像本身就从同一窗口（基址 0x20100000）执行到 0x2042BC10，追加区紧接其后，指针全为绝对 VA、无重定位。

静态分析**不能**证明的：该窗口在真机上对 0x2042BC10 之后的取指/取数确实有效——窗口译码范围属硬件/启动配置，代码里没有可供核对的尺寸常量。所以探针就是判据本身：它的代码与字库全在追加区、标题必须经洞穴代码绘制，标题正确显示即证明追加区可执行、可取数。失败形态也预先写明：标题空白/乱码 = 取数异常；完全不开机 = 取指异常；恢复走第四章的维护屏路径——而恢复路径本身同样未在真机实测过，与构建报告的风险声明一致。

### 8.6 复检 verdict 汇总

| 检查项 | 结论 |
|---|---|
| MAIN 字符串通道（名称/标题/对话框/页签） | **proven** |
| MAIN 值标签长度合同 | **defective → 已修复（V0114）** |
| DISPLAY 渲染补丁（入口/测量/洞穴/字库/旁路） | **proven** |
| 追加区 / XIP | **supported-but-unproven**（探针即验证手段） |
| Diff 审计与哈希 | **proven** |
| 基线锁与刷机说明 | **proven**（MAIN 改刷 V0114） |

复检这一章的教训和手台那章正好是一对：手台 v1 的错是**存储找错了**（表在，通道错）；FT-710 的错是**存储找对了、合同看漏了一条**（字段宽度对，长度常数错）。两种错都不会被"diff 只落在允许区域内"这类审计抓出来——它们只会被"逐条追代码如何消费这份数据"抓出来。

## 九、现状与刷机顺序

**现状：未上真机。** 到发稿为止，这套固件的全部证据是文件级（往返、diff、回读）、模拟器级（启动 + 渲染直调差分）和审计级（独立工具重算）的；硬件验证为零。第一次刷机就是探针那一刷，它同时是 XIP 假设、长镜像写入、维护屏标题三件事的判据。

刷机顺序（逐个刷、逐个验，不跳步）：

**前置**：设置备份到 SD → 升官方 202402 基线（先 DISPLAY V0108、后 MAIN V0112）→ 确认 SOFT VERSION 为 MAIN V01-12 / DISPLAY V01-08 且 DST 仍 CHINA。SD 卡常备原厂 `FT-710_MAIN_V0112.SFL` + `FT-710_DISPLAY_V0108.SFL`（恢复屏要求两个都 Ready）。每次刷机时，SD 卡 `FT-710\` 文件夹里每种类型只放当前要刷的那一个文件，文件名不改（更新器同类多文件时取字典序最大者，V0113 务必移走，不要和 V0114 同放）。

1. **探针 DISPLAY V0110**（SHA256 `ed10f7c6f2c81a7d94381cefd886026ec592d05bd13aa982fb225401b2ca4b72`）：菜单 `SETUP → SD CARD → FIRMWARE UPDATE` 只勾 DISPLAY。确认点：① 正常开机进主界面；② 主界面 ASCII 显示与平常无异；③ 关机按住 DNR + A/B + QMB 开机进维护屏，转主旋钮超过 4 步，标题应为「**中文菜单测试 FT-710**」。看完关机——**不要在解锁的维护屏上发起任何更新**（会写 loader 区）。
2. **全量 DISPLAY V0111**（SHA256 `cf6e1e9280b80cd9cc4119fd8b9a7d2a9bbe661ceed9ed6a996ae9dde609f495`）：同法刷入。确认点：开机正常；进 FUNC 菜单翻几页——此时菜单仍是英文（MAIN 还没换），但渲染路径已是全量版，ASCII 必须无花屏、无错位。
3. **MAIN V0114**（SHA256 `7684f90a235dfe3739a934ec321b87d60719744d77594bcdad51133fee75111c`）：同法只刷 MAIN。确认点：菜单变中文；逐页抽查条目名、值标签（特别是橙色高亮值如 `葡萄牙语(巴西)`，以及第八章修过的后置/编/正/反与月份显示）、P1/P2 标题、一个对话框（如 FORMAT 确认框）与信息记忆屏；核对 SOFT VERSION 屏 DST 仍为 CHINA。
4. 任一步不对：刷回该步的原厂文件，不要继续往下刷。MAIN 无应答时走 DISPLAY 的两步恢复屏（先 MAIN 后 DISPLAY）；DISPLAY 异常时走维护屏重刷官方 V0108。

真机结果出来之后会在这里补记——尤其是探针标题那一张照片，它值前面全部的静态分析。
