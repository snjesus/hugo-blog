# DMR 语音头的哒哒声：300 Hz 提示音与一个错配的 DMR ID

> DMR 发射时，语音头有哒哒声。在 NRL 听到，DMR→NRL 方向；NRL→DMR 和 NRL→YSF 都没问题。这篇记录哒哒声是怎么查的：它不在桥里，是电台那边发出来的一个干净的 300 Hz 单音正弦提示音，被桥原样传到 NRL；以及顺带查出来的另一个问题——热点错用了桥的 DMR ID。
>
> 前情在[上一篇](/posts/xlx-ysf-dt-rewrite/)（XLX 2.5.3 的 DT 改写）和[上上篇](/posts/xlx-dmr-ysf-nrl-topology/)（新拓扑与 DMR 杂音）。三篇都是 11 月 28 日同一天的工作。

---

## 现象

11 月 28 日 14:57，我报：DMR 发射时，语音头会有哒哒声。

方向确认过：在 NRL 听到，DMR→NRL 方向（BR4SN 从 DMR 发过来，我在 NRL 听到开头哒哒）。从 NRL 到 DMR、从 NRL 到 YSF 都没问题。所以只查 DMR→NRL 这条路：DMR 电台 → 热点 → XLX → dmr_bridge 收 AMBE+2 → MD380 固件解码 → PCM → AGC → Opus 编码 → SvxReflector → nrl_bridge → NRL。

## 桥侧三处都已排除

先排除桥：

- **全链路离线仿真开头平滑，无爆音。** 用桥自己的代码（filter.go、agc.go、resample.go 原样拷贝）和同一套 Opus 库/参数（8kHz AppVoIP 16kbps c5 → 16kHz AppVoIP 36kbps c10），对 BR4SN 14:55:28 的 132 帧 AMBE 做了全链路离线仿真。最终 16kHz PCM（即 NRL 客户端会播的）开头平滑：前 15 帧 RMS 0.7→39 渐升、峰值 ≤116、帧边界跳变 ≤10、头 300ms 内最大逐采样跳变仅 24。无爆音、无断点、无咔哒。
- **MD380 解码没有启动瞬态。** 同一帧 AMBE 在三种解码器初态（全新、静音预热 10 帧、语音预热 10 帧）下解出的 PCM 几乎相同，帧 0 最大样本差仅 14–22（满量程 32768，可忽略）。两次传输都验证过。
- **AGC 没有跳变。** dmr_bridge 的 AGC_EXT_TO_SVX 与 nrl_bridge 的 AGC_SVX_TO_EXT 都在 TalkerStart 时复位到增益 1.0，然后按 attack 平滑爬升（DMR 桥 0.05/帧、NRL 桥 0.01/帧），仿真里增益轨迹是 1.000→1.050→1.098→1.143→1.185，无跳变。AGC 只会造成缓慢淡入，不会出哒哒声。

与最近三处改动也无关：B+C 只改了 dmr_bridge 的 maxGain 与 NRL→DMR 目标电平，DMR→NRL 的 AGC 目标仍是 0.3；xlxd 重启/DT 修复只改 YSF 转发帧的 DT 标注，DMR 帧只是经 XLX 转发、内容不动；ysf_bridge 停用是另一条桥、另一条路。

## 爆音在 AMBE 源头就已存在

14:55:56 那次传输（src=4602468，stream 9B230000，2.6 秒）解出的 PCM：f0 RMS 5.5、f1 27.2，**f2 203.7、f3 431.3（峰值 888）、f4 156.2、f5 114.5**，f6 起回落到 17–25。全链路仿真后最终音频 f3 RMS 595.8、f4 RMS 941.7、峰值 2125，帧间跳变达 207–317。爆音在 AMBE 帧里就已存在，解码器初态换三遍也消不掉，AGC 只是以约 1.1 倍增益把它传过去。爆音持续约 80ms（f2–f5），之后 2.5 秒近乎静音——像一次空按 PTT 带出的按键/提示音，而非语音。

BR4SN 14:55:28 那次真人语音传输则全程平滑、开头干净，说明这不是每发必有的桥侧毛病。

## 旧问题，不是新问题

爆音在 AMBE 源头就存在，与 B+C、xlxd、ysf_bridge 三处改动都碰不到 DMR→NRL 的音频内容。之前没人提，很可能是因为之前 DMR→NRL 音量太轻（RMS 326）把爆音也压在听阈之下，AGC D 方案把它抬到正常电平后，爆音跟着浮出来了——与上一篇里杂音的结论是同一机制：**电平正常化后，原本听不见的东西被听见。**

## 决定性发现：爆音 100% 只出现在源 ID 4602468 的传输里

14:55:56 之后又有三次新的 DMR→NRL 传输（抓包 `/tmp/dmr_tick.pcap` 覆盖到 15:20）：

| 时间 | 流 ID | 源 ID | 时长 | 爆音 | 头 3 帧 AMBE |
|---|---|---|---|---|---|
| 15:14:54 | d7970000 | 4602468 | 5.2s | **有**（f2 RMS 203.7/峰值 827，f3 RMS 456.5/峰值 888） | 与 14:55:56 逐字节相同 |
| 15:15:26 | c77f0000 | 4602468 | 8.4s | **有**（f2 RMS 203.7/峰值 827，f3 RMS 431.3/峰值 888） | 与 14:55:56 逐字节相同 |
| 15:19:24 | 9b6e0000 | 4601256 | 3.9s | **无**（f0–f3 RMS 2.8–8.6，峰值 ≤34，平滑起音） | 与 14:55:28 逐字节相同 |

五次传输汇总：**src=4602468 的三次全有爆音，src=4601256 的两次全干净。爆音与源 ID 完全相关。**

补充：15:14:54 那次爆音后 1–3 秒是静音，3–5 秒才是真人语音（RMS 1249）；15:15:26 爆音后 1–5 秒与 6–8 秒都是真人语音。说明爆音与语音是分开的两段——先是爆音，后是说话。

## 爆音到底是什么声音：300 Hz 单音正弦提示音

用 MD380 固件声码器解出三个爆音传输的头 8 帧，做 Goertzel 扫频加 FFT 加自相关：

| 帧 | RMS | 峰值 | 零交叉 | 主导频率 |
|---|---|---|---|---|
| f0 | 5.5 | 16 | 60 | ~300Hz（极弱） |
| f1 | 27.2 | 88 | 15 | ~225Hz |
| f2 | 203.7 | 827 | 12 | ~225Hz |
| f3 | 431.3 | 888 | 12 | ~300Hz（最强） |
| f4 | 19.6–156.2 | 51–399 | 19–39 | 杂散 |
| f5 | 19.2–295.0 | 65–1645 | 15–30 | 杂散 |

**FFT（f2–f5 拼接）**：能量集中在 281–336 Hz，峰值 297–305 Hz，三次传输一致。**自相关**：最佳周期 26–27 采样 → 296–308 Hz。**波形**（f3 前 24 采样，三次传输逐采样相同）：

```
-689, -592, -395, -223, -60, 112, 225, 320, 406, 458, 509, 564, 592, 611, 615, 586, 525, 432, 295, 115, -102, -325, -574, -715
```

这是平滑周期正弦波，峰值因数（crest）约 2.0。**结论：单音 ~300 Hz 正弦提示音，持续约 80ms（f2–f5），幅度峰值 ~888。**

为什么不是按键机械声：机械按键咔哒是宽带瞬态（能量分散在全频段、无固定周期），而这是单一频率、平滑正弦、每次逐字节相同的确定性信号——只能是 DSP 生成的提示音。

为什么不是其他噪声：f0–f1 极轻（RMS 5.5→27.2），f2 起音、f3 达峰、f4–f5 衰减，是典型的“提示音包络”（起音–峰值–衰落），不是持续噪声。

最可能的来源是电台的 talk-permit 提示音（或 PTT 按键提示音）。多数电台在提示音期间静音话筒、对方听不到；但有的电台的提示音会被发出去（即在发射前先放一段短提示音）。4602468 这台属于后者——提示音期间话筒未静音，提示音被编码进 AMBE 发出来了。

品牌定不了：300 Hz 这个音调偏低，是 distinctive 指纹（在 DMR 语音带 300–3000 Hz 的最底端，多数提示音是 880–2000 Hz），但没有公开资料给出某品牌提示音是 300 Hz。TYT MD-380、AnyTone D878UV、摩托罗拉 MOTOTRBO、海能达都有 Talk Permit 提示音设置，要定品牌必须看电台实物。

干净传输的开机就是真静音：两个干净传输（14:55:28、15:19:24，src=4601256）的头 8 帧，f0–f3 RMS 2.8–8.6、峰值 ≤34，f3 前 12 采样两次传输逐采样相同，就是静音/底噪。爆音与干净的区别，确实就是“提示音开 vs 关”（或“提示音会发出 vs 不会发出”）的区别。

## 顺带查出来的另一个问题：热点错用了桥的 DMR ID

**热点 DMR ID 已证实就是 4602468。** 三重证据：

1. **语音帧源 ID**：四次 DMR→NRL 传输里，三次（14:55:56、15:14:54、15:15:26）的 DMRD 帧 src 字段全是 4602468；`dmrid.dat` 查得 `4602468 = BD4TWU`（桥的呼号），`4601256 = BD4TWO`（我的呼号）。热点发出的帧用的是桥的 DMR ID。
2. **xlxd 日志**：14:55:56、15:14:54、15:15:26 三次开流都记为 `Opening stream on module G for client BR4SN B`——这三次爆音传输确系 BR4SN 的热点（49.84.96.129）发出。
3. **同一热点双源 ID**：同一台热点（49.84.96.129，注册为 BR4SN）先后发出 src=4601256 与 src=4602468 两种帧。说明经这台热点的电台里，至少有一台的 DMR ID 被配成了 4602468（桥的 ID），而不是 BR4SN 自己的 ID。

最可能场景是有**两台不同的电台**（或两个人）在用这台热点，理由：① 源 ID 交替出现；② 语音响度差异大（4602468 的语音 RMS 965–1669，4601256 的仅 263–694——同一台电台只改 ID 不会改变话筒增益/响度）；③ 开机模式完全不同（一台有 300 Hz 提示音，一台真静音）。

- **4601256 那台**：最可能是我自己的电台（ID 与呼号 BD4TWO 一致），或 BR4SN 的电台被写成了我的 ID。干净、话筒增益较低。
- **4602468 那台**：最可能是 BR4SN 的电台，但 DMR ID 被错写成了桥的 4602468（BD4TWU），且 talk-permit/按键提示音开着并会被发出。话筒增益较高、语音更响。

未证实：BR4SN 真正的 DMR ID 到底是多少（数据里找不到，dmrid.dat 无 BR4SN 的登记）；到底是热点 Pi-Star 配置里的 DMR ID 被写成 4602468，还是某台电台自身的 DMR ID 被写成 4602468（VPS 侧看不到 Pi-Star 配置与电台写频，需 BR4SN 在热点/电台侧核对）。

顺带一提：NRL→DMR 方向的 4602468 是正常的——桥向 DMR 发射时源 ID 就是它自己的 4602468（BD4TWU），这是桥的合法身份。只有 DMR→NRL 方向出现 4602468 才是电台错用了桥的 ID。

## 给 BR4SN 的核对清单

按顺序做，改完发 3–5 次验证：

1. **查电台型号**：把 4602468 那台电台的品牌/型号报上来（爆音的 300 Hz 定不了品牌，必须看实物）。
2. **关提示音**：在该台电台上找提示音设置并关掉——
   - TYT MD-380/390：菜单 → Utilities（实用工具）→ Radio Settings（电台设置）→ Tones/Alerts（提示音/告警）→ **Talk Permit（通话允许）** 设为 Off；
   - AnyTone D878UV：Menu → Settings（设置）→ Sound（声音）→ **Talk permit tone（通话允许提示音）** 关；或 CPS 里对应信道的 **Talk permit beeps** 字段取消；
   - 摩托罗拉 MOTOTRBO：CPS → 信道 → **Talk Permit Tone（通话允许提示音）** 取消勾选；
   - 海能达：CPS → 常规设置/信道 → **通话允许提示音** 关；
   - 通用：同时确认 **Keypad Tones（按键音）** 与 **PTT Sidetone（PTT 边音）** 是否开了，开了也关掉。
3. **核对 DMR ID（两台都查）**：
   - 查热点 Pi-Star 配置（Configuration → General → **DMR ID**）当前写的是多少；
   - 查每台电台写频软件（CPS）里的 **DMR ID / Radio ID** 各是多少；
   - 目标：任何一台电台的 DMR ID 都**不能**是 4602468（那是桥 BD4TWU 的 ID）；BR4SN 自己的正确 DMR ID 是多少（4601256 登记为 BD4TWO，不是他的），查到后把错的那台改回他自己的正确 ID。
   - 顺带确认 4601256 那台：若它是 BR4SN 的电台却用了我的 ID，也要一并改回。
4. **验证**：改完后用 4602468 那台电台连续发 3–5 次、每次 3–5 秒，报每次的源 ID 与开头有无哒哒声。抓包 `/tmp/dmr_tick.pcap`（PID 114401，仍在跑）会对照每次发射的头几帧 AMBE 与源 ID。

备选的桥侧 workaround（在 dmr_bridge 的 CallStart 后丢弃头 1–2 个 AMBE 帧，或对头 60ms 做淡入）不建议首选：根因在源头，桥侧切帧是掩盖；而且会吃掉真正语音的头 20–40ms，爆音若在 40ms 之后仍会漏出。先按上面的清单确认复现规律与来源。

取证在 VPS `/tmp/`：抓包 `dmr_tick.pcap`（PID 114401，仍在跑，抓 62030 + 5300）；提取 `ambe_from62030_*.txt`；分析 `tick_analyze.py`、`full_profile.py`、`scan_dmrd.py`、`deep_analyze.py`、`deep_analyze2.py`；全链路仿真 `/tmp/opus_sim/opus_sim`。
